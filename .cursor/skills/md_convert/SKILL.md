# md_convert

把一份原始周报 Markdown，按本项目的格式规范，转换成符合规范的新 Markdown。

转换规则不是凭空发挥：它由三份项目内文件共同定义——

- `format_require.md`：**规范（spec）**，是硬性要求的唯一权威来源。
- `target.md`：**最终目标模板**，展示规范落地后的样子（章节结构、标识符、mermaid 写法等）。
- `convert.py`：**已有参考实现**，体现了哪些转换已经能力化、用什么配置化写法实现。

这三份文件通常在项目根目录。开始任何工作前先定位并通读它们。

- **保留原则**：当原始文档的指标、章节、表格、树状图等比 `target.md` 更多时，**倾向保留原文内容**，不要为了对齐模板而删减或移动。`target.md` 是**示例模板**，不是内容上限。

## 最重要的一条规则：先计划，后动手

每一次原始报告的措辞、数据、甚至规则细节都不一样，所以这是一个**人在环中**的工作流，不是一键脚本。

**在用户明确说"可以开始/同意/执行"之前，严禁创建或修改任何转换脚本、严禁生成转换后的 md。** 这一步只能产出"计划"和"讨论"。

之所以这么严，是因为用户对自己的报告了如指掌，但规则可能本次有变、目标版式可能要调整。让用户先确认计划，能避免你基于错误假设大改一通、产出南辕北辙的结果。计划获批后再写脚本，返工成本最低。

如果你发现自己在用户点头前就想读/写 `.py` 或写转换后的 md，停下来——那违反了本 skill 的核心。

## 工作步骤

### 第 1 步：确定原始 md 文件

- 如果用户在消息里**已经指明**了要转换哪个文件（文件名、@ 引用、或上下文明显只有一个候选），直接采用，并复述一句确认（"本次转换 `xxx.md`，对吗？"）。
- 如果**没有指明或有歧义**，先列出项目里候选的 .md（排除 `format_require.md`/`target.md` 这类规范文件），让用户选；不要替用户猜。

### 第 2 步：通读输入，给出修改计划

定位并读完这四样东西，再动脑：

1. 原始 md（第 1 步确定的那份）——它实际长什么样、有哪些章节/表格/树/逻辑链。
2. `format_require.md`——本次涉及到的硬性规则（标题与日期、章节骨架、表格、blockquote、逻辑链关键字+箭头、mermaid 树、趋势图、异常表、树状图等）。
3. `convert.py`——已有实现覆盖了哪些转换、用的什么配置化套路（便于复用，少造轮子）。
4. `target.md`——最终应该长成的样子，作为版式对照。

然后产出一份**具体、可核对**的修改计划，逐项说明"原文这样 → 规范要求那样 → 打算怎么改"。计划应覆盖（按本次实际涉及的部分裁剪）：

- 文档标题与日期是否需要规范化。
- 章节骨架与标题层级（一、总结 / 二 / 三 的命名与 `#` 级别）。
- 知识库命中事件字段是否补全（事件/出处/命中原因/事件描述/关联度）。
- 维度下钻 ASCII 树 → mermaid，并**保留原始数据**（贡献/环比写进节点 label，参考 `target.md` 节点样例）。
- 表格列改名（如 预警→异常说明）、分隔行对齐。
- 十对标识符的插入位置与判定依据（**标识符不再与章节严格绑定，检测到对应内容即插入，无论在第几章**）：
  - `!summary1_str!/!summary1_end!` — 块级包裹 section 一的全部内容
  - `!summary2_str!/!summary2_end!` — 块级包裹各指标节的 现象+分析 blockquote（典型位置：二章各指标节）
  - `!dau_summary_str!/!dau_summary_end!` — DAU 关键描述句，行内包裹（典型位置：一章总结）
  - `!revenue_summary_str!/!revenue_summary_end!` — 收入关键描述句，行内包裹（典型位置：一章总结）
  - `!logic_lib_str!/!logic_lib_end!` — 知识库命中事件块，块级包裹（典型位置：二章各指标节）
  - `!logic_train_str!/!logic_train_end!` — 逻辑链块，块级包裹（典型位置：二章各指标节）
  - `!dau_trend_str!/!dau_trend_end!` — DAU 趋势数据表，块级包裹（典型位置：二章各指标节）
  - `!revenue_trend_str!/!revenue_trend_end!` — 收入趋势数据表，块级包裹（典型位置：二章各指标节）
  - `!trend_str!/!trend_end!` — 通用趋势数据表（非 DAU/非收入），块级包裹（典型位置：二章各指标节）
  - `!tree_str!/!tree_end!` — mermaid 树状图，块级包裹（典型位置：二章各指标节）
- 任何 `target.md` 体现、但 `convert.py` 尚未覆盖的差异，要显式标出，并说明本次脚本是否补上。

把计划清楚地呈现给用户。涉及版式抉择（如章节是否按 `target.md` 重构）或规则歧义时，明确点出来请用户拍板，不要自作主张。

### 第 3 步：与用户对齐，直到获得明确同意

用户可能对计划有异议、有补充规则、或改主意。逐条回应、更新计划，再次确认。**反复迭代，直到用户明确表示同意。** 在此之前不得进入第 4 步。

### 第 4 步：生成本次专用脚本 + 转换后的 md

获得明确批准后：

1. **以 `convert.py` 为模板复制**一份本次专用脚本，放到项目根目录下的 `convert/` 文件夹，命名为 `convert_<原文件名>.py`），不要直接改 `convert.py` 本体（保留它作为通用参考）。
2. 按本次确认的计划，在复制出的脚本里调整**配置常量与规则**。沿用 `convert.py` 的风格：原文内容、转换结果、格式/别名/标识符都写成顶部可配置常量，正文一律从输入文件解析，**不要把业务文本写死**——因为原文每次都不同、规则也可能再变。
3. 运行脚本，生成**一份**转换后的 md（命名如 `<原文件名>_converted.md`，除非用户另有要求）。
4. **自检**：把产出和 `target.md` 规范、以及计划逐项对照；若有偏差就修脚本重跑。可用 diff 对比，确认改动只包含计划内的项。
5. 向用户汇报：生成了哪个脚本、哪个 md，做了哪些转换，还有哪些已知未覆盖项。

## 产出约定

- 一次转换 = 一个专用脚本（从 `convert.py` 复制改） + 一份转换后的 md。
- 不改动 `convert.py`、`format_require.md`、`target.md` 这三份源文件。
- 脚本保持配置化、可复跑、不硬编码业务文本。
