## 一、需求背景

#### **产品功能现状：**

- 目前 App 内仍在使用旧版品牌色，需统一更新为最新品牌色。得益于此前 icon 字体化改造已完成，本次全局换色的成本将大幅降低（可直接为 icon 赋色，无需开发再手动替换切图资源）
- 当前产品视觉规范中的颜色，主要沉淀在设计工具（如 Figma Variables / Styles）中。落地到代码时，常见做法是：设计交付标注色值（HEX / RGBA），开发在业务代码中手动添加变量色值，改色时依赖口头同步、文档截图或反复对照设计稿。

#### **现行模式的弊端：**

- 一致性差。同一语义色（如主按钮、危险提示、次要文案）在不同页面或项目可能对应不同色值，品牌与体验漂移；
- 变更成本高、易漏改。一次品牌色或暗色模式调整，需要全库搜色值、逐个替换；漏改会导致半新半旧；
- 协作摩擦大。设计与开发反复确认具体灰阶或色值，沟通成本占用双方有效产能（目前线上新旧颜色系统共存，旧颜色系统ab开头，不同开发可能用错，导致还原核对成本也非常高）；
- 缺乏可追溯性。无法回答某次线上色偏来自哪次改色，影响了哪些组件；
- 主题扩展困难。暗色模式、节日皮肤、多品牌白标等若仍靠硬编码，几乎要复制一整套样式逻辑，维护成本高；
- 设计资产无法工程化复用。Figma 变量与代码变量割裂，设计系统看起来有规范，工程侧实际仍是散装色值。

目标链路为：设计工具定义颜色变量 &rarr; 导出/同步为按 Key 组织的 Token 文件 &rarr; 提交至 Git 仓库（评审、版本、权限）&rarr; 构建或包分发至各业务项目 &rarr; 开发通过 Key 调用（如 background/brand 或 text/secondary）。

## 二、功能目标

### **总体目标：建立「颜色 Token 入库 + Key 调用」的标准协作模式，使颜色成为可版本管理、可工程消费的设计系统资产。**
**1、颜色资产规范化（设计侧）**
颜色从零散色值升级为统一、有语义的 Token 清单，设计侧定义更清晰、用途更明确。改色、扩主题、做暗色时，只需调整映射关系，不必反复核对零散色值，从源头减少「同名不同色」和临时色滥用。
**2、Git 仓库托管与发布（工程协作）**
颜色资产变更可追溯、可回滚。设计确认后的色板能稳定同步到各业务，避免口头通知、文档粘贴导致的信息滞后和漏改，真正形成「以仓库发布版为准」的单一事实源。
**3、 研发 Key 调用（消费侧）**
开发按语义 Key 取色，无需关心具体 HEX，也少做查稿对色。主题切换时只换上下文、不改业务代码；结合 icon 字体化，全局换品牌色可直接赋色，不必再手动替换切图，改色成本与漏改风险都明显下降。
**4、协作与治理**
新增、废弃、升版有明确规则，设计与研发对齐同一套命名与流程。页面默认走 Key，长期把「能不能随便加色、怎么合法改色」变成可执行规范，而不是靠个人习惯和临时沟通。

## 五、需求描述

**UI设计：**

- 在 Figma中维护一套 颜色变量库：baseColor 负责定义颜色梯度（如蓝、灰、红等色阶的原始色值）；functionColor 负责定义颜色变量的 Key（如主色、文案色、背景色、状态色等语义用途）。业务与组件优先通过 functionColor 的 Key 调用颜色；functionColor 再映射到对应的 baseColor 梯度值。这样改色时通常只调映射关系，不必改业务侧调用的 Key。

- 按照Candy Toolkit插件的命名规则调整颜色变量命名，主要是改为驼峰命名法（camelCase）：图标名称的首字母为小写，后续单词首字母大写。例如：addUser, notificationBell, arrowDown。
- 颜色变量通过 Candy Toolkit 上传至 Git 仓库。后续新增或调整变量映射时，无需开发手动改代码，开发侧一键拉取仓库最新代码即可同步生效。

**开发：**

- 只通过 functionColor 的 Key 取色，不要在业务里写死 HEX/RGBA，尽量不要直接依赖 baseColor 梯度（除非做底层能力）。

- 颜色变更以 Git 仓库发布版为准。新增或调整映射后，用约定方式一键拉取最新颜色变量，不要本地私改色板或拷贝一份旁路维护。

- Code Review 卡点：新增 UI 若出现裸色值，应改为 functionColor Key；确需临时色时走白名单或提需补 Token，避免再次散落。

- 不要擅自重命名、删除已在用的 Key。废弃由设计侧走流程；开发侧按兼容策略迁移，避免线上缺色或回退异常。

- 联调验收看「Key + 仓库版本」是否正确，而不是只盯某一帧截图色差；若视觉不对，先核对是否拉到最新仓、映射是否发布，再反馈设计。

- 线上旧的颜色系统替换成新的Git颜色系统，旧颜色系统弃用
