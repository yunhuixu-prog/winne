## 一、需求背景

#### **产品功能现状：**
目前 App 采用的是传统静态资源管理模式：iOS图标以 PNG的形式、安卓图标以SVG 文件形式存在于客户端工程中，开发根据文件名硬编码调用
迭代流程：设计师导出 @2x/@3x 切图 -> 交付开发 -> 开发手动替换 -> 重新编译打包。

#### **现行模式的弊端：**
这种"写死"在客户端内的做法，在项目规模扩大后会暴露出以下几个致命问题：
❌ 内存与包体臃肿
冗余资源多：为了适配不同分辨率，每个图标通常需要准备 2~3 套位图（@2x, @3x）。
颜色限制：同个图标若有 5 种颜色，就得存 5 张切图，导致包体积线性增长。
内存占用：位图渲染时占据的内存远高于矢量描述文件。
❌ 协作链路极长
沟通成本高：设计师每次改动一个小圆角，都需要重新发图、改名。
开发负担：开发需要手动管理成百上千的图标变量名，极易出错。
❌ 视觉表现力受限
失真模糊：位图在非标准缩放比例下（或 UI 临时调整大小时）会出现锯齿或模糊。
缺乏动态灵活性：无法通过代码实时改变图标颜色、透明度**（因为之前改一次颜色耗费资源精力较多，目前App内icon的颜色还没有更新为最新品牌色）**
❌ 多端一致性难保障
iOS和Android 往往各自维护一套切图。一旦设计规范更新，需要两端端同步更换，极其容易产生视觉差异。

目前业界成熟方案均已实现图标矢量化管理。引入 Git 托管图标字体，不仅是为了减少包体大小，更是为了实现设计工程化，让 UI 迭代不再受限于繁琐的切图交付

## 二、功能目标

**1、减重：**将数百张位图整合为单个字体文件，显著降低包体积。
**2、增效：**实现图标在代码层面的颜色控制与任意缩放，减少重复交付。
**3、统一：**建立以 Git 为核心的"单一事实来源"，确保 iOS、Android、H5 视觉一致。
